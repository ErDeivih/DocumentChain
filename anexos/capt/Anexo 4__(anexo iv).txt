2.1 PATRONES DE ARQUITECTURA Y DE DISEÑO
En este apartado se plantearán los distintos patrones arquitectónicos que se
utilizarán para el correcto diseño e implementación del sistema.

2.1.1 PATRÓN BACKEND FOR FRONTEND (BFF)
El patrón BFF o Backend-For-Frontend es un patrón de diseño software enfocado
a servicios REST.
Con este patrón se enfoca el desarrollo del backend según las necesidades del
frontend, con lo que priorizamos la interfaz de usuario y las opciones que esa UI
necesita. Así, el desarrollo se centrará principalmente en el usuario y en la interfaz con
la que trabajará, desarrollando una API REST totalmente personalizada para dicho
frontend (aunque dicha API podría usarse para otro tipo de aplicaciones).

Ilustración 1. Patrón BFF.

6

Anexo IV: Diseño del sistema software.

Este patrón es una variante del patrón API Gateway. Este otro patrón permite
centralizar y enrutar todas las peticiones hacia un servicio único y personalizado.

Ilustración 2. Patrón API Gateway.

Con el uso del patrón BFF como variante del patrón API Gateway se podrá enfocar
el sistema directamente a ofrecer los servicios únicamente necesarios para el correcto
funcionamiento de la web y para que los usuarios trabajen de forma cómoda con el robot
y la aplicación.

2.1.2 PATRÓN ACCESS TOKEN
El patrón Access Token es un patrón arquitectónico que sirve para autenticar,
utilizando para ello un token de acceso, las peticiones enviadas. Este patrón trabaja
junto al patrón API Gateway explicado en el apartado anterior para un correcto desarrollo
de la API REST.

Ilustración 3. Patrón Access Token con JWT

7

Anexo IV: Diseño del sistema software.
Gracias al uso de este patrón, podemos ofrecer distintos servicios a través de la API
y protegerlos (o no) ante usuarios no deseados. Esto se hará utilizando un token JWT
para la autenticación de usuarios que se generará de forma única o se eliminará cuando
un usuario haga login o logout en el sistema respectivamente (o en caso de que expire
el tiempo de uso del token).

2.1.3 PATRÓN FACADE
El patrón Facade o Fachada es un patrón de diseño estructural que actúa de
intermediario ocultando la complejidad para acceder a un determinado objeto o servicio,
proporcionando para ello una interfaz de alto nivel con la que acceder de una manera
mucho más sencilla y legible para el programador.

Ilustración 4. Patrón Facade.

Este patrón se utilizará para enmascarar en un objeto en el servidor Frontend (web)
toda la lógica necesaria para hacer las peticiones al servicio correspondiente del
servidor Backend (API REST).

2.2 SUBSISTEMAS DE DISEÑO
Una vez superada la etapa de análisis del proyecto y establecidos los patrones
arquitectónicos que se utilizarán durante el diseño, se realiza una división del sistema
en subpaquetes más específicos dentro de la estructura general de la aplicación:
•

•

Servidores: este subpaquete del sistema hace referencia a los dos
servidores desarrollados siguiendo el patrón BFF (Backend For Frontend)
explicado anteriormente: el servidor web o frontend y el servidor api o
backend. En cada servidor a su vez nos encontramos con varios paquetes:
o Servidor web o frontend: servidor que proporciona la web a los
distintos usuarios para soliticar la preparación de bebidas al robot,
gestionar el robot, gestionar los datos de la aplicación, etc. Incluye 2
subpaquetes:
▪ Vista web: hace referencia a las distintas páginas web que
verán los usuarios y donde se les presentará la información.
▪ ControladorPeticiones: hace referencia a un objeto que será
el encargado de hacer las peticiones a la API del servidor
backend para trabajar con los distintos datos y con el robot.
Este controlador sirve como fachada (patrón Facade) para las
vistas que necesitan
o Servidor API o backend: servidor encargado de proporcionar una
API a medida para el backend (patrón BFF) para poder trabajar con
los distintos datos almacenados en el sistema y con el propio robot.
Este servidor se encargará de procesar las peticiones recibidas por el
servidor frontend y gestionar los datos, además de realizar las
peticiones necesarias hacia la API del robot. Contiene 2 subpaquetes:
▪ ControladorAPI: recoge toda la lógica necesaria para ofrecer
los distintos servicios a través de rutas (API) y se encarga
además de comunicarse con el robot según esas peticiones
recibidas.
▪ DatosBarbot: incluye todos los datos almacenados en el
sistema, tanto los datos guardados en la base de datos como
las imágenes de las recetas (se guardarán en el backend
mientras que se guardará la ruta a dichas imágenes en la base
de datos para no sobrecargarla).
Robot: este subpaquete representa todo el robot en conjunto, incluyendo
tanto el firmware a instalar para el movimiento del robot como la API expuesta
para poder comunicarse con él y la web para poder gestionarlo. Este paquete
incluye:
o APIRobot: subpaquete que incluye toda la funcionalidad referente a
la API con la que el servidor backend se comunicará para gestionar el
robot y la web a la que podrá acceder el administrador para poder ver
el estado del robot. Se divide a su vez en 2 subpaquetes:
▪ ControladorAPIRobot: incluye toda la funcionalidad para la
comunicación con el robot.
▪ Vista web robot: incluye la web para la gestión del robot.
o FirmwareRobot: incluye toda la funcionalidad dentro del controlador
de los motores necesaria para convertir las órdenes enviadas por el
ControladorAPIRobot para el movimiento del robot.

3 DISEÑO DE LA BASE DE DATOS
Para que el sistema pueda almacenar y gestionar correctamente la información, se
utilizará una base de datos MySQL. En esta base de datos se guardarán diferentes
tablas correspondientes a los datos de los usuarios, bebidas, recetas y otros de interés
para el sistema.
Esta base de datos se describe según el siguiente modelo de entidad relación:

Ilustración 54. Diseño de la base de datos.

La base de datos dispondrá de las siguientes tablas principales:
•
•
•
•
•

Roles: roles que puede tener un usuario.
Users: información de los usuarios
Cocktails: información sobre las recetas
Drinks: información sobre las bebidas
Drink_positions: información sobre las posiciones del robot y las bebidas
registradas en ellas.

Estas tablas se relacionan a través de otras tablas (o directamente entre ellas) de la
siguiente forma:
•
•

•

User_roles: tabla intermedia que almacena los roles que tiene cada usuario.
Sirve como unión para la relación N:M entre las tablas Roles y Users.
User_stats: tabla intermedia que almacena las estadísticas que tiene cada
usuario para cada receta registrada. Sirve como unión para la relación N:M
entre las tablas Cocktails y Users.
Cocktail_drinks: tabla intermedia que almacena las bebidas que componen
cada receta registrada. Sirve como unión para la relación N:M entre las tablas
Cocktails y Drinks.

50

Anexo IV: Diseño del sistema software.
La última relación es la relación N:1 entre las tablas Drinks y Drink_positions. Con
esta relación se expresa el número de bebidas que puede haber en cada posición
(que es 1) pero que esta bebida puede repetirse en varias posiciones.

4 MODELO DE DESPLIEGUE
El modelo de despliegue se representa utilizando para ello un diagrama de
despliegue. Este diagrama muestra la arquitectura de ejecución de un sistema,
incluyendo para ellos entornos de ejecución hardware, software y los middlewares que
los conectan.
El diagrama de despliegue del sistema diseñado es el siguiente:

Ilustración 55. Diagrama de despliegue.

Como se puede observar en la figura, el sistema se compone de los siguientes nodos:
•

•

•

•

Dispositivo con acceso a páginas web: dispositivo que dispone de un
navegador web que permite acceder a páginas web. Con estos dispositivos
los usuarios podrán acceder a la web del sistema y realizar distintas acciones.
Servidor web Frontend: servidor que sirve de vista para el usuario.
Proporciona la web a la que accederán los distintos usuarios. Se trata de un
