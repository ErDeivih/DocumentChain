\section{Propósito del anexo}

Este anexo se plantea como una guía de apoyo para la defensa y para la explicación posterior del sistema desde la perspectiva de implementación, despliegue e integración. No sustituye a la memoria principal ni a los anexos funcionales. Tampoco reemplaza al nuevo Anexo VI, centrado en la arquitectura blockchain, Solidity e IPFS. Aquí se recogen argumentos técnicos complementarios, decisiones de infraestructura y criterios útiles para responder preguntas del tribunal con un hilo expositivo claro.

\section{Dualidad entre blockchain y base de datos relacional}

La arquitectura del sistema se apoya en dos capas de persistencia que no compiten entre sí, sino que resuelven problemas distintos. La blockchain se utiliza cuando interesa una evidencia inmutable, verificable por terceros y resistente a modificaciones posteriores. La base de datos PostgreSQL se utiliza cuando interesa consulta rápida, flexibilidad de modelado, enriquecimiento de la información y soporte operativo de la aplicación.

En la práctica, la blockchain conserva la parte mínima cuya alteración resultaría más sensible desde el punto de vista de trazabilidad: identificadores de documentos, relaciones de propiedad, permisos efectivos, operaciones de compartición, cambios de versión operativa y firmas digitales. Esa información tiene valor porque puede ser contrastada de forma independiente y porque permite demostrar que un evento existió y quedó registrado en un instante determinado.

La base de datos, por su parte, mantiene el estado de trabajo que la interfaz necesita para ser utilizable. Se almacenan usuarios, sesiones, preferencias, notificaciones, carpetas, etiquetas, métricas, relaciones auxiliares, estados de sincronización y proyecciones pensadas para consulta. También se guardan datos derivados o históricos que sería ineficiente, costoso o directamente improcedente mantener en cadena. Un ejemplo claro es la proyección de firmantes enriquecida con instantáneas de perfil, que permite seguir mostrando nombre visible, alias o wallet incluso si la relación viva con el usuario cambia más adelante.

Desde la defensa conviene transmitir que la blockchain no sustituye a la base de datos generalista. Se emplea como capa de confianza y de no repudio, mientras que PostgreSQL actúa como capa operativa y de servicio. Si todo se dejara en blockchain, la aplicación sería cara, rígida y lenta para casos de uso cotidianos. Si todo se dejara en la base de datos, se perdería la garantía externa de inmutabilidad que da sentido al sistema.

\section{Uso de Docker en el proyecto}

Docker se utiliza como mecanismo de reproducibilidad del entorno. La idea principal consiste en evitar que la ejecución local dependa del estado concreto de la máquina donde se clona el repositorio. Al encapsular PostgreSQL, Hardhat, Postfix, backend y frontend, se reduce el número de dependencias manuales que una tercera persona tendría que instalar para poner el sistema en marcha.

Desde el punto de vista de la defensa, Docker aporta tres mensajes fáciles de justificar. En primer lugar, facilita la entrega porque permite levantar el sistema con una única orquestación. En segundo lugar, separa responsabilidades por servicio, lo que encaja con una arquitectura moderna y desacoplada. En tercer lugar, acerca el entorno de desarrollo a un despliegue realista, ya que frontend, backend, SMTP y base de datos se ejecutan como servicios distintos con dependencias explícitas.

En este proyecto, la contenerización también ha servido para dejar preparado el frontend en una imagen de producción y no solo como servidor de desarrollo de Vite. Eso permite mostrar una ejecución más cercana a un escenario de despliegue real, con Nginx sirviendo la SPA ya construida y proxy inverso hacia la API.

\section{Por qué se utiliza Nginx}

Nginx cumple una función concreta en el frontend dockerizado. No se ha incorporado como adorno, sino como servidor HTTP ligero para servir los archivos estáticos generados por Vite, resolver correctamente el enrutado de la SPA y redirigir las llamadas a \texttt{/api} hacia el backend.

Sin esta capa, sería necesario exponer el frontend de otra manera o introducir lógica adicional en otro servicio. Nginx simplifica ese trabajo porque resuelve tres problemas habituales de una SPA en producción. El primero consiste en servir los archivos estáticos con una huella operativa pequeña. El segundo consiste en devolver \texttt{index.html} cuando el usuario entra directamente en una ruta interna del frontend. El tercero consiste en evitar problemas de configuración separando la URL visible del frontend de la URL interna del backend dentro de Docker.

En una defensa puede resumirse diciendo que Nginx se usa como servidor de publicación del frontend y como proxy de integración entre interfaz y API. No es estrictamente la única solución posible, pero sí una solución estándar, sencilla y apropiada para una entrega seria.

\section{Configuración completa del correo electrónico}

El subsistema de correo está dividido en dos planos. El backend genera los mensajes y decide cuándo enviarlos. Postfix actúa como servidor SMTP de salida dentro del entorno Docker. Esa división evita que la lógica de negocio dependa de un proveedor concreto y permite cambiar la estrategia de entrega sin reescribir el servicio de correo del backend.

En local, el backend puede entregar al Postfix interno usando \texttt{SMTP\_HOST}, \texttt{SMTP\_PORT}, \texttt{SMTP\_USER} y \texttt{SMTP\_PASS}. Cuando Postfix no tiene un relay configurado, intenta entrega directa a los servidores de destino. Esa modalidad resulta válida para integración básica o demostración controlada, pero no conviene presentarla como solución fiable para Internet abierta. La reputación del emisor dependerá entonces de que exista IP fija, puerto 25 saliente sin bloqueo, PTR inverso correcto y registros SPF, DKIM y DMARC adecuados.

Para una salida real a Internet, la opción recomendada consiste en configurar Postfix como relay hacia un proveedor SMTP. El contenedor admite variables como \texttt{SMTP\_RELAYHOST}, \texttt{SMTP\_RELAYHOST\_USERNAME}, \texttt{SMTP\_RELAYHOST\_PASSWORD} y \texttt{POSTFIX\_SMTP\_TLS\_SECURITY\_LEVEL}. De este modo, el backend sigue hablando con el SMTP interno del proyecto, mientras que Postfix delega la entrega final en un servicio con mejor reputación y menor probabilidad de rechazo.

\subsection{Configuración validada en el entorno del proyecto}

Durante la fase final de integración se ha dejado operativa una configuración concreta que permite enviar mensajes reales desde el entorno Docker a una bandeja de Gmail. El flujo adoptado no utiliza entrega MX directa, sino relay autenticado. El backend entrega primero al contenedor \texttt{postfix}; a continuación, Postfix reenvía el mensaje a Brevo mediante autenticación SMTP y canal TLS. El remitente visible se ha fijado en una dirección previamente verificada en el proveedor de relay, de forma que la salida resulte coherente con las políticas del servicio.

En la práctica, la configuración activa se apoya en un fichero \texttt{.env} situado en la raíz del proyecto, consumido por \texttt{docker-compose}. En él se definen, entre otras, las siguientes variables: \texttt{SMTP\_HOST=postfix}, \texttt{SMTP\_PORT=587}, \texttt{SMTP\_SECURE=false}, \texttt{SMTP\_RELAYHOST=[smtp-relay.brevo.com]:587}, \texttt{SMTP\_RELAYHOST\_USERNAME}, \texttt{SMTP\_RELAYHOST\_PASSWORD}, \texttt{EMAIL\_FROM} y \texttt{EMAIL\_FROM\_NAME}. El frontend continúa resolviéndose con \texttt{FRONTEND\_URL}, lo que permite generar enlaces válidos hacia \texttt{/verify-email}, \texttt{/reset-password}, \texttt{/login} y las rutas autenticadas usadas en los avisos operativos.

La decisión de mantener Postfix como capa intermedia sigue teniendo sentido aunque se utilice un relay externo. El backend queda desacoplado del proveedor y puede seguir trabajando siempre contra un mismo host SMTP interno. Si más adelante se cambia Brevo por otro servicio, la modificación se concentra en la configuración de Postfix y no en la lógica de generación de mensajes ni en las plantillas del backend.

\subsection{Proceso interno de envío}

El proceso de envío comienza en el servicio \texttt{emailService.ts}. Ese servicio compone el asunto, selecciona la plantilla HTML adecuada y resuelve las URLs visibles en el correo a partir de \texttt{FRONTEND\_URL}. Cuando se dispara una acción como registro, verificación de correo, recuperación de contraseña, aviso de documento compartido o notificación asociada a una nueva versión, el backend renderiza la plantilla con \textit{Handlebars} y delega el transporte en Nodemailer.

Nodemailer no se conecta directamente al proveedor externo en la configuración final. El transporte apunta al SMTP interno del proyecto, es decir, al contenedor \texttt{postfix}. Una vez recibido el mensaje, Postfix aplica su configuración de relay, negocia TLS con Brevo y entrega el mensaje a \texttt{smtp-relay.brevo.com}. El proveedor acepta el correo, lo pone en cola para salida y realiza la entrega final hacia la bandeja del destinatario. Ese encadenamiento puede describirse de forma compacta como \textit{backend $\rightarrow$ Postfix $\rightarrow$ relay SMTP $\rightarrow$ destinatario final}.

Desde el punto de vista operativo, el esquema aporta dos ventajas. Por un lado, simplifica las pruebas locales porque todo el código del backend sigue enviando contra un host conocido dentro de Docker. Por otro, permite inspeccionar con claridad en qué punto falla el proceso, ya que pueden revisarse tanto los logs del backend como la cola y los logs de Postfix antes de atribuir el problema al proveedor SMTP.

\subsection{Incidencia observada con entrega directa y criterio adoptado}

Se llegó a probar una variante en la que Postfix intentaba entregar directamente a los MX públicos de Gmail. La experiencia mostró que esa vía no era adecuada en el entorno de trabajo empleado para el proyecto. La entrega quedaba diferida por problemas de conectividad saliente y por las limitaciones habituales de reputación de un emisor local sin infraestructura de correo plenamente publicada. En términos prácticos, el sistema conseguía generar y encolar los mensajes, pero la salida final no era fiable.

Ese resultado no se interpretó como un fallo de la aplicación, sino como una consecuencia esperable del contexto de red. Por esa razón se adoptó el relay autenticado como solución final. De cara a la defensa conviene señalar que el código ya estaba correctamente desacoplado y que el cambio se limitó a ajustar la infraestructura SMTP de salida, no a rediseñar el backend.

\subsection{Qué hace falta para que el correo salga bien a Internet}

Si se quiere una configuración realmente utilizable fuera del entorno local, todavía hacen falta varios elementos ajenos al código. Es necesario disponer de un dominio desde el que se vaya a enviar correo, acceso a su zona DNS, una cuenta o credenciales SMTP del proveedor elegido y la decisión de cuál será la dirección visible de salida. También conviene fijar si se va a utilizar entrega directa con infraestructura propia o relay a través de un tercero. Para una entrega académica o una primera producción pequeña, la ruta más razonable suele ser relay autenticado con proveedor SMTP.

En términos prácticos, lo que deberá prepararse es lo siguiente: credenciales SMTP válidas del relay, dominio emisor, registro SPF, clave DKIM publicada, política DMARC básica y una URL pública definitiva del frontend para que los enlaces de verificación no apunten a \texttt{localhost}. Cuando esos datos estén disponibles, el proyecto ya podrá configurarse sin cambios estructurales grandes.

\subsection{Tipos de correo actualmente activos}

En el estado consolidado del proyecto se mantienen los correos vinculados a operaciones claras de negocio: verificación de cuenta, restablecimiento de contraseña, confirmación de cambio de contraseña, bienvenida tras el alta, documento compartido y notificaciones operativas. Se ha retirado el envío específico de alerta de seguridad independiente porque introducía ruido para el escenario del TFG y repetía información que el sistema ya muestra en la propia aplicación. También se ha revisado el contenido de las plantillas para que los enlaces apunten a rutas existentes y para que el tono del mensaje resulte consistente con el resto de la interfaz.

Esa revisión ha incluido la supresión de elementos decorativos innecesarios, la mejora del contraste de los botones y la eliminación de referencias a dirección IP o dispositivo en los mensajes de cambio de contraseña. El objetivo no ha sido únicamente estético; también se ha buscado que el contenido sea defendible y exacto desde el punto de vista funcional.

\subsection{Verificación y diagnóstico}

La comprobación del subsistema de correo puede realizarse sin ambigüedad siguiendo una secuencia breve. Primero se revisa que \texttt{docker compose ps} muestre operativos los contenedores \texttt{backend} y \texttt{postfix}. Después se lanza una acción que fuerce un correo real, por ejemplo una verificación de cuenta o un restablecimiento de contraseña. A continuación se inspeccionan los logs de Postfix para confirmar la aceptación del relay y se valida que la cola quede vacía. Si el proveedor responde con códigos de aceptación \texttt{250 2.0.0 OK}, el problema, en caso de existir, ya no se encuentra en la aplicación sino en políticas posteriores del proveedor o del destinatario.

En la defensa puede explicarse que esa secuencia permitió localizar con precisión cada incidencia encontrada durante la integración. Primero se comprobó que el backend generaba el mensaje. Después se verificó que Postfix lo aceptaba. Finalmente se aisló la diferencia entre la entrega MX directa, que fallaba en red, y la entrega mediante relay autenticado, que sí permitía llegada efectiva a Gmail.

\section{Argumento de defensa recomendado}

Si se pregunta por la motivación global de la arquitectura, puede defenderse que el sistema separa deliberadamente lo que necesita confianza externa de lo que necesita operatividad. Blockchain se reserva para evidencia, permisos y trazabilidad fuerte. PostgreSQL se reserva para consultas, relaciones auxiliares y rendimiento. Docker se utiliza para asegurar repetibilidad del entorno. Nginx se usa para publicar el frontend de forma coherente con una SPA real. El correo se abstrae a través de SMTP y Postfix para no acoplar la lógica del backend a un proveedor concreto. Esa combinación permite explicar que el proyecto no es una simple demo de blockchain, sino una aplicación completa que intenta equilibrar verificabilidad, rendimiento y capacidad de despliegue.

\section{Nuevas funcionalidades consolidadas}

Durante la fase final de desarrollo se han incorporado tres capacidades que completan la experiencia de usuario y la transparencia del sistema:

\begin{itemize}
    \item \textbf{Avatar de perfil con almacenamiento local}. El backend expone \texttt{PUT /users/me/avatar} y \texttt{DELETE /users/me/avatar}. La imagen se almacena en disco (\texttt{uploads/avatars/}) y se sirve como recurso estático. El campo \texttt{avatarUrl} se añadió al modelo \texttt{User} de Prisma. El frontend muestra la imagen en la cabecera y en la vista de perfil, y refresca el contexto de autenticación tras cada cambio.
    \item \textbf{Eliminación de cuenta con firma blockchain}. El endpoint \texttt{DELETE /users/me} recibe un \texttt{txHash} correspondiente a una transacción \texttt{suspendMyself} firmada por la wallet principal. El backend valida la transacción on-chain, desancla los CIDs de IPFS asociados a los documentos del usuario, elimina el avatar del disco y ejecuta \texttt{prisma.user.delete()} en cascada. Esta operación es irreversible y mantiene inmutables los registros ya existentes en blockchain.
    \item \textbf{Auditoría por hash de transacción}. El endpoint público \texttt{GET /audit/transaction/:txHash} consulta el \textit{provider} de Ethereum, recupera el \textit{receipt}, decodifica los logs con el ABI del contrato y enriquece los eventos con metadata de PostgreSQL (nombre del documento, visibilidad, \texttt{publicId}). Esto permite a cualquier usuario explorar una transacción concreta sin autenticación, de forma similar a Etherscan pero especializada en el dominio documental.
    \item \textbf{Identificadores copiables (CopyableId)}. El componente \texttt{CopyableId} trunca visualmente identificadores largos (\texttt{documentId}, \texttt{blockchainId}) y ofrece un botón para copiar el valor completo al portapapeles, con confirmación visual mediante \textit{toast}. Se utiliza en la vista de detalle del documento y en paneles de administración, reduciendo la fricción cuando el usuario necesita compartir o buscar un identificador concreto.
    \item \textbf{Mensajes legibles en firma blockchain y mapeo de errores}. El servicio \texttt{signatureService.ts} del backend genera un \texttt{messageToSign} en texto plano que incluye el título del documento, la versión y la dirección del contrato, de forma que la wallet muestre al usuario qué está firmando antes de confirmar. En el frontend, la función \texttt{getErrorMessage()} de \texttt{lib/api.ts} centraliza el mapeo de 11 patrones de error blockchain (revert, fondos insuficientes, nonce, red incorrecta, gas, firma duplicada, etc.) a mensajes comprensibles en español, evitando que el usuario reciba trazas técnicas crudas.
\end{itemize}
