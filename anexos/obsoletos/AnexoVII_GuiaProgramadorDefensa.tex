\section{Propósito del anexo}

Este anexo se plantea como una guía de apoyo para la defensa y para la explicación posterior del sistema desde la perspectiva de implementación, despliegue e integración. No sustituye a la memoria principal ni a los anexos funcionales. Tampoco reemplaza al nuevo Anexo VI, centrado en la arquitectura blockchain, Solidity e IPFS. Aquí se recogen argumentos técnicos complementarios, decisiones de infraestructura y criterios útiles para responder preguntas del tribunal con un hilo expositivo claro.

\section{Dualidad entre blockchain y base de datos relacional}

La arquitectura del sistema se apoya en dos capas de persistencia que no compiten entre sí, sino que resuelven problemas distintos. La blockchain se utiliza cuando interesa una evidencia inmutable, verificable por terceros y resistente a modificaciones posteriores. La base de datos PostgreSQL se utiliza cuando interesa consulta rápida, flexibilidad de modelado, enriquecimiento de la información y soporte operativo de la aplicación.

En la práctica, la blockchain conserva la parte mínima cuya alteración resultaría más sensible desde el punto de vista de trazabilidad: identificadores de documentos, relaciones de propiedad, permisos efectivos, operaciones de compartición, cambios de versión operativa y firmas digitales. Esa información tiene valor porque puede ser contrastada de forma independiente y porque permite demostrar que un evento existió y quedó registrado en un instante determinado.

La base de datos, por su parte, mantiene el estado de trabajo que la interfaz necesita para ser utilizable. Se almacenan usuarios, sesiones, preferencias, notificaciones, carpetas, etiquetas, métricas, relaciones auxiliares, estados de sincronización y proyecciones pensadas para consulta. También se guardan datos derivados o históricos que sería ineficiente, costoso o directamente improcedente mantener en cadena. Un ejemplo claro es la proyección de firmantes enriquecida con instantáneas de perfil, que permite seguir mostrando nombre visible, alias o wallet incluso si la relación viva con el usuario cambia más adelante.

Desde la defensa conviene transmitir que la blockchain no sustituye a la base de datos generalista. Se emplea como capa de confianza y de no repudio, mientras que PostgreSQL actúa como capa operativa y de servicio. Si todo se dejara en blockchain, la aplicación sería cara, rígida y lenta para casos de uso cotidianos. Si todo se dejara en la base de datos, se perdería la garantía externa de inmutabilidad que da sentido al sistema.

\subsection{Escritura: el patrón prepare/confirm como puente entre mundos}

Las operaciones que modifican el estado documental y requieren evidencia on-chain no se ejecutan en un único paso, porque la firma de la transacción debe realizarse con la clave privada del usuario, que nunca abandona su wallet. Para coordinar esa separación sin dejar la base de datos en un estado intermedio inconsistente, el backend implementa un patrón \textit{prepare/confirm}.

\textbf{Fase prepare.} Cuando el usuario solicita crear un documento, una versión o una firma, el backend realiza todo aquello que no requiere firma blockchain: valida permisos, cifra el binario con AES-256-GCM cuando el documento es privado, sube el resultado a IPFS, genera los identificadores necesarios y crea un registro en PostgreSQL con estado \texttt{PREPARING}. En ese momento la fila ya existe en la base de datos, pero el campo \texttt{blockchainTxHash} está vacío y el estado indica que falta la confirmación on-chain. La respuesta al frontend incluye los datos que la wallet necesita para construir la transacción: \texttt{docId}, \texttt{ipfsCid}, identificador interno del recurso y, cuando procede, el \texttt{publicId}.

\textbf{Fase confirm.} El frontend usa esos datos para construir la transacción, la firma con la wallet del usuario y la envía a la red. Una vez que dispone del \textit{transaction hash}, llama al endpoint de confirmación del backend. Este endpoint recibe el hash y el identificador blockchain, localiza el registro previamente preparado y actualiza su estado a \texttt{TX\_SUBMITTED}, almacenando el \texttt{txHash} y el \texttt{blockchainId} correspondientes. A partir de ese instante el sistema sabe que la transacción ha sido emitida, pero aún no sabe si será minada con éxito.

\textbf{Sincronización final.} Un trabajador periódico (\texttt{blockchainSync.ts}) consulta cada cinco minutos los registros en estado \texttt{TX\_SUBMITTED} y pide el \textit{receipt} de cada transacción al proveedor Ethereum. Si el \textit{receipt} indica éxito (\texttt{status === 1}), el registro pasa a \texttt{SYNCED}. Si la transacción fue revertida (\texttt{status === 0}) o no se encuentra (fue descartada por la red), el estado cambia a \texttt{FAILED} y se anota el motivo del error. Este mismo flujo se aplica a documentos, versiones y firmas, de modo que cada entidad lleva su propio \texttt{blockchainStatus} y \texttt{blockchainTxHash}.

La ventaja arquitectónica de este patrón es que la base de datos siempre tiene una versión autoritativa del estado, incluso si el usuario abandona el flujo después de la preparación o si la transacción blockchain fracasa. El frontend puede reconstruir la situación a partir de PostgreSQL sin depender de que la cadena responda en tiempo real.

\subsection{Consultas del cliente: ¿dónde se resuelve cada petición?}

Una pregunta frecuente en la defensa es dónde busca el sistema la información cuando el usuario interactúa con la interfaz. La respuesta corta es que casi siempre consulta PostgreSQL, pero verifica blockchain cuando se requiere una comprobación de autoridad o cuando el dato on-chain es el único que no puede ser alterado por el operador del servidor.

\textbf{Listados, búsquedas y paginación.} Cuando el usuario abre su panel de documentos, aplica filtros por nombre, tipo, carpeta o estado de archivo, el backend resuelve la consulta exclusivamente contra PostgreSQL. Los campos \texttt{name}, \texttt{mimeType}, \texttt{folderId}, \texttt{tags}, \texttt{isArchived} y \texttt{createdAt} viven en la base de datos, lo que permite ordenar, filtrar y paginar con el rendimiento habitual de un motor relacional.

\textbf{Detalle de documento y metadatos.} La vista de detalle de un documento muestra información enriquecida que solo existe en PostgreSQL: nombre, descripción, tamaño, extensión, avatar del propietario, lista de versiones con comentarios, instantáneas de perfil de los firmantes y relaciones de carpetas. Ningún dato de esa proyección se lee directamente de la blockchain, porque la cadena no almacena esos atributos.

\textbf{Permisos y acceso.} El smart contract es la única fuente de verdad para autorización. Cuando el backend necesita saber si un usuario puede ver, editar o compartir un documento, consulta directamente el contrato \texttt{DocumentRegistry} mediante \texttt{canView}, \texttt{canEdit} o \texttt{isOwner}. PostgreSQL conserva el campo \texttt{ownerId} únicamente como cache de optimización para listados de lectura, pero nunca se utiliza como criterio de autorización en operaciones destructivas (crear versiones, compartir, transferir, firmar). El campo \texttt{blockchainId} debe existir antes de cualquier operación que requiera validación de permisos; si no existe, el sistema rechaza la operación. Esta decisión arquitectónica elimina la dualidad entre base de datos y blockchain, garantizando que un compromiso de PostgreSQL no pueda otorgar privilegios no confirmados on-chain.

\textbf{Descarga de contenido.} Para descargar un archivo, el backend consulta PostgreSQL para obtener el \texttt{ipfsCid} de la versión operacional, recupera el binario cifrado del nodo IPFS y devuelve al frontend los metadatos de descifrado (clave simétrica cifrada, IV y etiqueta de autenticación) que también están almacenados en la base de datos. La blockchain solo interviene indirectamente: el CID que figura en PostgreSQL debe coincidir con el que eventualmente quedó registrado on-chain, pero la descarga en sí no consulta la cadena.

\textbf{Auditoría y verificación externa.} El endpoint público \texttt{GET /audit/transaction/:txHash} es la excepción que confirma la regla: aquí el backend consulta directamente el proveedor Ethereum, recupera el \textit{receipt} de la transacción y decodifica los logs del contrato usando su ABI. Ese endpoint no toca PostgreSQL para la verificación criptográfica, aunque sí enriquece los eventos decodificados con metadatos de la base de datos (nombre del documento, visibilidad, \texttt{publicId}) para hacer la respuesta comprensible.

\textbf{Estados de sincronización.} El frontend puede preguntar en cualquier momento por el \texttt{blockchainStatus} de un documento, versión o firma. Esa información siempre se lee de PostgreSQL, porque es el backend quien la mantiene actualizada a través del patrón \textit{prepare/confirm} y del sincronizador. El cliente no necesita conectarse directamente a la blockchain para saber si una operación ya fue confirmada.

\subsection{Sincronización y reconciliación de estados}

Mantener coherencia entre dos capas de persistencia con semánticas tan distintas requiere mecanismos explícitos. El sistema dispone de tres:

\textbf{1. Sincronización por confirmación inmediata.} En la fase \textit{confirm}, tras actualizar el registro a \texttt{TX\_SUBMITTED}, el backend intenta de forma optimista obtener el \textit{receipt} de la transacción. Si la red local (Hardhat) ya ha minado el bloque, el receipt estará disponible y el sistema actualiza inmediatamente el registro a \texttt{SYNCED}, creando además el evento \texttt{DOCUMENT\_CREATED} o equivalente con el número de bloque y la marca temporal. Esto reduce la ventana de inconsistencia a segundos.

\textbf{2. Worker de sincronización periódica.} El archivo \texttt{blockchainSync.ts} programa dos tareas con \texttt{node-cron}. Cada cinco minutos revisa los registros en \texttt{TX\_SUBMITTED} y consulta sus receipts; cada treinta minutos busca registros en \texttt{PREPARING} cuya antigüedad supere los treinta minutos y los marca como \texttt{FAILED}, asumiendo que el usuario nunca firmó la transacción. Este worker actúa como red de seguridad cuando la confirmación inmediata no tuvo éxito.

\textbf{3. Event listener en tiempo real.} El servicio \texttt{eventListenerService.ts} se suscribe a los eventos del contrato \texttt{DocumentRegistry} tanto históricos (mediante \texttt{queryFilter}) como en tiempo real (mediante \texttt{on}). Cuando detecta un evento como \texttt{DocumentCreated}, \texttt{VersionCreated} o \texttt{DocumentSigned}, compara la información on-chain con el estado de PostgreSQL. Si encuentra discrepancias ---por ejemplo, una firma que existe en blockchain pero que el backend no había registrado--- actualiza o crea el registro correspondiente y notifica a los usuarios afectados. Este mecanismo también permite detectar operaciones realizadas directamente sobre el contrato sin pasar por la interfaz web.

El resultado es que PostgreSQL funciona como una réplica operativa eventualmente consistente con la blockchain. No se exige consistencia inmediata en cada milisegundo, pero sí se garantiza que, en un horizonte de minutos, cualquier operación exitosa on-chain quedará reflejada en la base de datos.

\subsection{Manejo de inconsistencias y recuperación}

A pesar de los mecanismos anteriores, pueden producirse situaciones anómalas que el sistema debe resolver sin intervención manual.

\textbf{Transacción revertida.} Si la transacción firmada por el usuario revierte on-chain (por ejemplo, por un modificador \texttt{notArchived} o una condición de permisos), el \textit{receipt} indica \texttt{status === 0}. El backend marca el registro como \texttt{FAILED} y conserva el \texttt{txHash} para que el usuario pueda consultar en el explorador de bloques qué ocurrió. El contenido ya subido a IPFS no se elimina automáticamente en ese momento, pero el registro en \texttt{FAILED} impide que la interfaz lo trate como un documento válido.

\textbf{Usuario abandona después de prepare.} Si el usuario cierra el navegador después de la fase \textit{prepare} y nunca firma la transacción, el registro queda en \texttt{PREPARING}. El worker de limpieza lo detecta pasados treinta minutos y lo marca como \texttt{FAILED}. En ese punto el binario sigue en IPFS, pero el backend podría implementar en el futuro un desanclado automático de CIDs huérfanos.

\textbf{Operación directa al contrato.} Si un usuario avanzado interactúa directamente con \texttt{DocumentRegistry} desde Etherscan o una herramienta similar, la base de datos no habrá pasado por \textit{prepare}. El event listener detectará el evento on-chain, pero al buscar el registro en PostgreSQL no lo encontrará o no coincidirán los identificadores. En esos casos el listener crea o actualiza lo que puede (por ejemplo, una firma o un cambio de permisos) y deja constancia en los logs para revisión manual.

\textbf{Uso de la tabla Event en confirmaciones.} La tabla \texttt{Event} se utiliza exclusivamente como log de auditoría y timeline visual. En las confirmaciones de shares, transferencias y revocaciones, el backend puede consultar \texttt{Event} para recuperar metadatos de conveniencia (por ejemplo, el identificador del destinatario), pero \textbf{nunca como paso obligatorio para la autorización}. La fuente de verdad definitiva sigue siendo la blockchain: el servicio valida el receipt de la transacción on-chain o consulta directamente el contrato antes de aceptar una confirmación. Este diseño garantiza que un compromiso de PostgreSQL no pueda confirmar una operación no autorizada.

\textbf{Reorganización de cadena.} En el entorno actual (red local Hardhat con finalidad inmediata) no se contemplan reorganizaciones de cadena (\textit{reorgs}). En un despliegue sobre red pública sería recomendable esperar un número de confirmaciones antes de considerar definitivo un evento, o implementar un mecanismo de reversión de registros recientemente sincronizados si aparece una reorganización en los bloques de mayor altura.

\section{Uso de Docker en el proyecto}

Docker se utiliza como mecanismo de reproducibilidad del entorno. La idea principal consiste en evitar que la ejecución local dependa del estado concreto de la máquina donde se clona el repositorio. Al encapsular PostgreSQL, Hardhat, Postfix, backend y frontend, se reduce el número de dependencias manuales que una tercera persona tendría que instalar para poner el sistema en marcha.

Desde el punto de vista de la defensa, Docker aporta tres mensajes fáciles de justificar. En primer lugar, facilita la entrega porque permite levantar el sistema con una única orquestación. En segundo lugar, separa responsabilidades por servicio, lo que encaja con una arquitectura moderna y desacoplada. En tercer lugar, acerca el entorno de desarrollo a un despliegue realista, ya que frontend, backend, SMTP y base de datos se ejecutan como servicios distintos con dependencias explícitas.

En este proyecto, la contenerización también ha servido para dejar preparado el frontend en una imagen de producción y no solo como servidor de desarrollo de Vite. Eso permite mostrar una ejecución más cercana a un escenario de despliegue real, con Nginx sirviendo la SPA ya construida y proxy inverso hacia la API.

\section{Por qué se utiliza Nginx}

Nginx cumple una función concreta en el frontend dockerizado. No se ha incorporado como adorno, sino como servidor HTTP ligero para servir los archivos estáticos generados por Vite, resolver correctamente el enrutado de la SPA y redirigir las llamadas a \texttt{/api} hacia el backend.

Sin esta capa, sería necesario exponer el frontend de otra manera o introducir lógica adicional en otro servicio. Nginx simplifica ese trabajo porque resuelve tres problemas habituales de una SPA en producción. El primero consiste en servir los archivos estáticos con una huella operativa pequeña. El segundo consiste en devolver \texttt{index.html} cuando el usuario entra directamente en una ruta interna del frontend. El tercero consiste en evitar problemas de configuración separando la URL visible del frontend de la URL interna del backend dentro de Docker.

En una defensa puede resumirse diciendo que Nginx se usa como servidor de publicación del frontend y como proxy de integración entre interfaz y API. No es estrictamente la única solución posible, pero sí una solución estándar, sencilla y apropiada para una entrega seria.

\section{Configuración completa del correo electrónico}

El subsistema de correo está dividido en dos planos. El backend genera los mensajes y decide cuándo enviarlos. Postfix actúa como servidor SMTP de salida dentro del entorno Docker. Esa división evita que la lógica de negocio dependa de un proveedor concreto y permite cambiar la estrategia de entrega sin reescribir el servicio de correo del backend.

En local, el backend puede entregar al Postfix interno usando \texttt{SMTP\_HOST}, \texttt{SMTP\_PORT}, \texttt{SMTP\_USER} y \texttt{SMTP\_PASS}. Cuando Postfix no tiene un relay configurado, intenta entrega directa a los servidores de destino. Esa modalidad resulta válida para integración básica o demostración controlada, pero no conviene presentarla como solución fiable para Internet abierta. La reputación del emisor dependerá entonces de que exista IP fija, puerto 25 saliente sin bloqueo, PTR inverso correcto y registros SPF, DKIM y DMARC adecuados.

Para una salida real a Internet, la opción recomendada consiste en configurar Postfix como relay hacia un proveedor SMTP. El contenedor admite variables como \texttt{SMTP\_RELAYHOST}, \texttt{SMTP\_RELAYHOST\_USERNAME}, \texttt{SMTP\_RELAYHOST\_PASSWORD} y \texttt{POSTFIX\_SMTP\_TLS\_SECURITY\_LEVEL}. De este modo, el backend sigue hablando con el SMTP interno del proyecto, mientras que Postfix delega la entrega final en un servicio con mejor reputación y menor probabilidad de rechazo.

\subsection{Configuración validada en el entorno del proyecto}

Durante la fase final de integración se ha dejado operativa una configuración concreta que permite enviar mensajes reales desde el entorno Docker a una bandeja de Gmail. El flujo adoptado no utiliza entrega MX directa, sino relay autenticado. El backend entrega primero al contenedor \texttt{postfix}; a continuación, Postfix reenvía el mensaje a Brevo mediante autenticación SMTP y canal TLS. El remitente visible se ha fijado en una dirección previamente verificada en el proveedor de relay, de forma que la salida resulte coherente con las políticas del servicio.

En la práctica, la configuración activa se apoya en un fichero \texttt{.env} situado en la raíz del proyecto, consumido por \texttt{docker-compose}. En él se definen, entre otras, las siguientes variables: \texttt{SMTP\_HOST=postfix}, \texttt{SMTP\_PORT=587}, \texttt{SMTP\_SECURE=false}, \texttt{SMTP\_RELAYHOST=[smtp-relay.brevo.com]:587}, \texttt{SMTP\_RELAYHOST\_USERNAME}, \texttt{SMTP\_RELAYHOST\_PASSWORD}, \texttt{EMAIL\_FROM} y \texttt{EMAIL\_FROM\_NAME}. El frontend continúa resolviéndose con \texttt{FRONTEND\_URL}, lo que permite generar enlaces válidos hacia \texttt{/verify-email}, \texttt{/reset-password}, \texttt{/login} y las rutas autenticadas usadas en los avisos operativos.

La decisión de mantener Postfix como capa intermedia sigue teniendo sentido aunque se utilice un relay externo. El backend queda desacoplado del proveedor y puede seguir trabajando siempre contra un mismo host SMTP interno. Si más adelante se cambia Brevo por otro servicio, la modificación se concentra en la configuración de Postfix y no en la lógica de generación de mensajes ni en las plantillas del backend.

\subsection{Proceso interno de envío}

El proceso de envío comienza en el servicio \texttt{emailService.ts}. Ese servicio compone el asunto, selecciona la plantilla HTML adecuada y resuelve las URLs visibles en el correo a partir de \texttt{FRONTEND\_URL}. Cuando se dispara una acción como registro, verificación de correo, recuperación de contraseña, aviso de documento compartido o notificación asociada a una nueva versión, el backend renderiza la plantilla con \textit{Handlebars} y delega el transporte en Nodemailer.

Nodemailer no se conecta directamente al proveedor externo en la configuración final. El transporte apunta al SMTP interno del proyecto, es decir, al contenedor \texttt{postfix}. Una vez recibido el mensaje, Postfix aplica su configuración de relay, negocia TLS con Brevo y entrega el mensaje a \texttt{smtp-relay.brevo.com}. El proveedor acepta el correo, lo pone en cola para salida y realiza la entrega final hacia la bandeja del destinatario. Ese encadenamiento puede describirse de forma compacta como \textit{backend $\rightarrow$ Postfix $\rightarrow$ relay SMTP $\rightarrow$ destinatario final}.

Desde el punto de vista operativo, el esquema aporta dos ventajas. Por un lado, simplifica las pruebas locales porque todo el código del backend sigue enviando contra un host conocido dentro de Docker. Por otro, permite inspeccionar con claridad en qué punto falla el proceso, ya que pueden revisarse tanto los logs del backend como la cola y los logs de Postfix antes de atribuir el problema al proveedor SMTP.

\subsection{Incidencia observada con entrega directa y criterio adoptado}

Se llegó a probar una variante en la que Postfix intentaba entregar directamente a los MX públicos de Gmail. La experiencia mostró que esa vía no era adecuada en el entorno de trabajo empleado para el proyecto. La entrega quedaba diferida por problemas de conectividad saliente y por las limitaciones habituales de reputación de un emisor local sin infraestructura de correo plenamente publicada. En términos prácticos, el sistema conseguía generar y encolar los mensajes, pero la salida final no era fiable.

Ese resultado no se interpretó como un fallo de la aplicación, sino como una consecuencia esperable del contexto de red. Por esa razón se adoptó el relay autenticado como solución final. De cara a la defensa conviene señalar que el código ya estaba correctamente desacoplado y que el cambio se limitó a ajustar la infraestructura SMTP de salida, no a rediseñar el backend.

\subsection{Qué hace falta para que el correo salga bien a Internet}

Si se quiere una configuración realmente utilizable fuera del entorno local, todavía hacen falta varios elementos ajenos al código. Es necesario disponer de un dominio desde el que se vaya a enviar correo, acceso a su zona DNS, una cuenta o credenciales SMTP del proveedor elegido y la decisión de cuál será la dirección visible de salida. También conviene fijar si se va a utilizar entrega directa con infraestructura propia o relay a través de un tercero. Para una entrega académica o una primera producción pequeña, la ruta más razonable suele ser relay autenticado con proveedor SMTP.

En términos prácticos, lo que deberá prepararse es lo siguiente: credenciales SMTP válidas del relay, dominio emisor, registro SPF, clave DKIM publicada, política DMARC básica y una URL pública definitiva del frontend para que los enlaces de verificación no apunten a \texttt{localhost}. Cuando esos datos estén disponibles, el proyecto ya podrá configurarse sin cambios estructurales grandes.

\subsection{Tipos de correo actualmente activos}

En el estado consolidado del proyecto se mantienen los correos vinculados a operaciones claras de negocio: verificación de cuenta, restablecimiento de contraseña, confirmación de cambio de contraseña, bienvenida tras el alta, documento compartido y notificaciones operativas. Se ha retirado el envío específico de alerta de seguridad independiente porque introducía ruido para el escenario del TFG y repetía información que el sistema ya muestra en la propia aplicación. También se ha revisado el contenido de las plantillas para que los enlaces apunten a rutas existentes y para que el tono del mensaje resulte consistente con el resto de la interfaz.

Esa revisión ha incluido la supresión de elementos decorativos innecesarios, la mejora del contraste de los botones y la eliminación de referencias a dirección IP o dispositivo en los mensajes de cambio de contraseña. El objetivo no ha sido únicamente estético; también se ha buscado que el contenido sea defendible y exacto desde el punto de vista funcional.

\subsection{Verificación y diagnóstico}

La comprobación del subsistema de correo puede realizarse sin ambigüedad siguiendo una secuencia breve. Primero se revisa que \texttt{docker compose ps} muestre operativos los contenedores \texttt{backend} y \texttt{postfix}. Después se lanza una acción que fuerce un correo real, por ejemplo una verificación de cuenta o un restablecimiento de contraseña. A continuación se inspeccionan los logs de Postfix para confirmar la aceptación del relay y se valida que la cola quede vacía. Si el proveedor responde con códigos de aceptación \texttt{250 2.0.0 OK}, el problema, en caso de existir, ya no se encuentra en la aplicación sino en políticas posteriores del proveedor o del destinatario.

En la defensa puede explicarse que esa secuencia permitió localizar con precisión cada incidencia encontrada durante la integración. Primero se comprobó que el backend generaba el mensaje. Después se verificó que Postfix lo aceptaba. Finalmente se aisló la diferencia entre la entrega MX directa, que fallaba en red, y la entrega mediante relay autenticado, que sí permitía llegada efectiva a Gmail.

\section{Argumento de defensa recomendado}

Si se pregunta por la motivación global de la arquitectura, puede defenderse que el sistema separa deliberadamente lo que necesita confianza externa de lo que necesita operatividad. Blockchain se reserva para evidencia, permisos y trazabilidad fuerte. PostgreSQL se reserva para consultas, relaciones auxiliares y rendimiento. Docker se utiliza para asegurar repetibilidad del entorno. Nginx se usa para publicar el frontend de forma coherente con una SPA real. El correo se abstrae a través de SMTP y Postfix para no acoplar la lógica del backend a un proveedor concreto. Esa combinación permite explicar que el proyecto no es una simple demo de blockchain, sino una aplicación completa que intenta equilibrar verificabilidad, rendimiento y capacidad de despliegue.

\section{Nuevas funcionalidades consolidadas}

Durante la fase final de desarrollo se han incorporado tres capacidades que completan la experiencia de usuario y la transparencia del sistema:

\begin{itemize}
    \item \textbf{Avatar de perfil con almacenamiento local}. El backend expone \texttt{PUT /users/me/avatar} y \texttt{DELETE /users/me/avatar}. La imagen se almacena en disco (\texttt{uploads/avatars/}) y se sirve como recurso estático. El campo \texttt{avatarUrl} se añadió al modelo \texttt{User} de Prisma. El frontend muestra la imagen en la cabecera y en la vista de perfil, y refresca el contexto de autenticación tras cada cambio.
    \item \textbf{Eliminación de cuenta con firma blockchain}. El endpoint \texttt{DELETE /users/me} recibe un \texttt{txHash} correspondiente a una transacción \texttt{suspendMyself} firmada por la wallet principal. El backend valida la transacción on-chain, desancla los CIDs de IPFS asociados a los documentos del usuario, elimina el avatar del disco y ejecuta \texttt{prisma.user.delete()} en cascada. Esta operación es irreversible y mantiene inmutables los registros ya existentes en blockchain.
    \item \textbf{Auditoría por hash de transacción}. El endpoint público \texttt{GET /audit/transaction/:txHash} consulta el \textit{provider} de Ethereum, recupera el \textit{receipt}, decodifica los logs con el ABI del contrato y enriquece los eventos con metadata de PostgreSQL (nombre del documento, visibilidad, \texttt{publicId}). Esto permite a cualquier usuario explorar una transacción concreta sin autenticación, de forma similar a Etherscan pero especializada en el dominio documental.
    \item \textbf{Identificadores copiables (CopyableId)}. El componente \texttt{CopyableId} trunca visualmente identificadores largos (\texttt{documentId}, \texttt{blockchainId}) y ofrece un botón para copiar el valor completo al portapapeles, con confirmación visual mediante \textit{toast}. Se utiliza en la vista de detalle del documento y en paneles de administración, reduciendo la fricción cuando el usuario necesita compartir o buscar un identificador concreto.
    \item \textbf{Mensajes legibles en firma blockchain y mapeo de errores}. El servicio \texttt{signatureService.ts} del backend genera un \texttt{messageToSign} en texto plano que incluye el título del documento, la versión y la dirección del contrato, de forma que la wallet muestre al usuario qué está firmando antes de confirmar. En el frontend, la función \texttt{getErrorMessage()} de \texttt{lib/api.ts} centraliza el mapeo de 11 patrones de error blockchain (revert, fondos insuficientes, nonce, red incorrecta, gas, firma duplicada, etc.) a mensajes comprensibles en español, evitando que el usuario reciba trazas técnicas crudas.
\end{itemize}


\section{Cifrado documental y protecci\'on de contenido}

El sistema no almacena documentos en texto plano. Cuando un usuario sube un archivo, el frontend genera una clave sim\'etrica aleatoria de 256 bits y cifra el contenido con AES-256-GCM antes de enviarlo al backend. Esta clave nunca abandona el navegador del usuario que crea el documento.

Para documentos privados, la clave sim\'etrica se protege mediante RSA-OAEP con la clave p\'ublica de cada usuario autorizado. Solo el destinatario con la clave privada correspondiente puede descifrar la clave sim\'etrica y, con ella, el documento. El backend solo ve bytes cifrados: ni el contenido ni la clave sim\'etrica transitan en texto plano por el servidor.

Cuando un documento es p\'ublico, la clave sim\'etrica se incluye en la metadata accesible sin autenticaci\'on, de modo que cualquier visitante puede descargar y descifrar el contenido desde el nodo IPFS. Esta diferencia entre privado y p\'ublico se decide en el momento de la creaci\'on y afecta tanto al cifrado como a la visibilidad de la metadata.

Si un usuario pierde su clave privada del navegador (almacenada en IndexedDB), no puede recuperar documentos privados de los que no sea propietario. El propietario original puede compartir de nuevo el documento, generando un nuevo envoltorio RSA-OAEP para el nuevo par de claves del usuario.

\section{Flujo \textit{prepare/confirm} y reconciliaci\'on}

La mayor\'ia de operaciones con trazabilidad blockchain siguen un patr\'on en dos fases para evitar estados inconsistentes entre PostgreSQL, IPFS y la cadena.

\textbf{Fase de preparaci\'on.} El backend crea un registro en PostgreSQL con estado \texttt{PENDING}, almacena el contenido en IPFS si procede, genera el mensaje legible para la wallet y devuelve los datos necesarios al frontend. En este punto no hay modificaci\'on on-chain.

\textbf{Fase de confirmaci\'on.} El usuario firma la transacci\'on con su wallet. El frontend env\'ia la firma al backend, que la valida y completa el registro on-chain. Si la transacci\'on es exitosa, el backend actualiza el estado a \texttt{SYNCED} y almacena el \texttt{txHash}. Si la transacci\'on revierte o el usuario rechaza la firma, el registro pasa a \texttt{FAILED} y se ofrece la opci\'on de reintentar.

Este patr\'on se aplica a: creaci\'on de documento, nueva versi\'on, firma, compartici\'on, transferencia, restauraci\'on de versi\'on y reactivaci\'on de cuenta. La ventaja principal es que el sistema siempre puede reconstruir el estado a partir de PostgreSQL, aunque la transacci\'on blockchain falle o el usuario abandone el flujo.

\section{Sincronizaci\'on de eventos blockchain}

El contrato \texttt{DocumentRegistry} emite eventos cada vez que ocurre una operaci\'on relevante: \texttt{DocumentCreated}, \texttt{VersionCreated}, \texttt{DocumentSigned}, \texttt{DocumentShared}, etc. El backend implementa un \textit{event listener} que consulta peri\'odicamente los bloques nuevos, filtra los logs por la direcci\'on del contrato y decodifica los argumentos usando el ABI.

Cuando el listener detecta un evento, compara la informaci\'on on-chain con el estado operativo en PostgreSQL. Si encuentra discrepancias (por ejemplo, una firma que aparece en blockchain pero no en la base de datos), actualiza el registro correspondiente y marca el documento como reconciliado. Este mecanismo tambi\'en permite detectar operaciones realizadas directamente sobre el contrato sin pasar por la interfaz web.

En caso de reorganizaci\'on de la cadena (\textit{reorg}), el sistema actualmente no revierte cambios autom\'aticamente, ya que el entorno de desarrollo usa una red local con finalidad inmediata. En un despliegue con redes p\'ublicas, se recomendar\'ia esperar un n\'umero de confirmaciones antes de considerar un evento como definitivo.

\section{Modelo de permisos on-chain}

El contrato define tres roles para cada documento:

\begin{itemize}
    \item \textbf{VIEWER (1):} puede descargar y verificar firmas.
    \item \textbf{EDITOR (2):} puede ver, descargar, crear versiones y firmar.
    \item \textbf{OWNER (3):} control total; puede compartir, firmar, transferir y eliminar.
\end{itemize}

Los permisos se almacenan en un mapping \texttt{\_permissions[documentId][address]} dentro del contrato. Cuando el backend necesita verificar si una operaci\'on est\'a permitida, consulta \textbf{exclusivamente} el contrato (mediante \texttt{canView}, \texttt{canEdit}, \texttt{isOwner}). PostgreSQL puede conservar proyecciones de listados para rendimiento, pero nunca interviene en la decisi\'on de autorizaci\'on. El smart contract es la \'unica fuente de verdad para permisos.

La transferencia de propiedad es irreversible on-chain. Cuando el propietario transfiere un documento, el contrato reasigna OWNER al nuevo usuario y revoca autom\'aticamente el rol del anterior. El backend replica este cambio en PostgreSQL y notifica a ambas partes.

\section{Estrategia de versionado}

Cada vez que se crea una nueva versi\'on, el sistema genera un nuevo CID en IPFS y un nuevo registro en blockchain. Las versiones anteriores no se sobrescriben; permanecen accesibles en el historial. El contrato mantiene una referencia a la \textit{versi\'on operativa} actual, que es la que se usa por defecto para descargas, firmas y compartici\'on.

La restauraci\'on de una versi\'on anterior no recupera el CID antiguo como operativo directamente, sino que crea una \textit{nueva versi\'on} que reutiliza el contenido y el hash de la anterior. Esto preserva el historial completo sin saltos: la l\'inea temporal siempre avanza, aunque el contenido operativo pueda ser id\'entico a uno anterior.

Cada versi\'on conserva su propia metadata de cifrado. En documentos privados, esto significa que la clave sim\'etrica de cada versi\'on est\'a protegida independientemente, de modo que revocar el acceso a una versi\'on no afecta a las dem\'as.

\section{Decisiones de seguridad arquitect\'onicas}

\textbf{Sin proxy upgradeable.} Aunque los patrones ERC-1967 permiten actualizar la l\'ogica de un contrato sin cambiar su direcci\'on, a\~naden complejidad y superficie de ataque. En este proyecto se prioriz\'o la claridad del c\'odigo y la reproducibilidad del entorno de pruebas. Cualquier modificaci\'on en \texttt{DocumentRegistry} exige un redeploy completo, lo cual es aceptable en un entorno acad\'emico y de demostraci\'on.

\textbf{Pausable.} El contrato hereda de \texttt{Pausable} de OpenZeppelin. Si se detecta un comportamiento an\'omalo, el propietario del contrato puede pausar las operaciones de escritura sin perder el estado acumulado. Esto act\'ua como un \textit{circuit breaker} de emergencia.

\textbf{Cifrado en cliente.} El backend nunca manipula el contenido en texto plano. El cifrado y descifrado ocurren en el navegador mediante Web Crypto API. Esto reduce la superficie de ataque del servidor: incluso si el backend se viera comprometido, los documentos privados permanecer\'ian inaccesibles sin las claves privadas de los usuarios.

\textbf{Notas de firma legibles.} En lugar de firmar hashes opacos, el backend genera un mensaje en texto plano que describe la operaci\'on. Esto protege al usuario de ataques de phishing donde un frontend malicioso podr\'ia solicitar la firma de una transacci\'on distinta a la esperada.

\section{Criterios de pruebas}

El proyecto mantiene dos suites de pruebas:

\textbf{Backend (Jest):} 177 tests distribuidos en 21 suites. Cubren l\'ogica de negocio, validaci\'on de permisos, manejo de errores blockchain, cifrado y descifrado, sincronizaci\'on de eventos y operaciones CRUD. No se prueban las interacciones reales con MetaMask ni la red Ethereum local, ya que estas se validan mediante tests de integraci\'on y E2E.

\textbf{E2E (Playwright):} 81 tests en Chromium que recorren los flujos completos de usuario: registro, login, subida de documento, firma, compartici\'on, verificaci\'on p\'ublica y administraci\'on. Los tests usan una wallet de pruebas inyectada y un entorno Docker Compose completo, garantizando que el sistema funciona de extremo a extremo.

Lo que no se cubre: pruebas de carga, pruebas con m\'ultiples nodos IPFS, pruebas de seguridad ofensiva (penetration testing) y pruebas con wallets hardware f\'isicas. Estas quedan como l\'inea de trabajo futura.

\section{Preguntas frecuentes del tribunal}

A continuaci\'on se recogen respuestas preparadas para las preguntas m\'as probables durante la defensa:

\textbf{-- \textquestiondown Por qu\'e blockchain y no una base de datos normal?}

Blockchain no sustituye a la base de datos; la complementa. PostgreSQL gestiona el estado operativo, las consultas, las relaciones y la interfaz. Blockchain aporta evidencia inmutable, verificable por terceros y resistente a modificaciones posteriores. Sin blockchain, un administrador del sistema podr\'ia alterar registros de firmas o permisos sin dejar rastro. Con blockchain, cualquier cambio relevante queda registrado en un libro mayor distribuido.

\textbf{-- \textquestiondown Qui\'en paga el gas en una red p\'ublica?}

En el entorno actual, la red es local (Hardhat) y no hay coste real. En una red p\'ublica, cada usuario pagar\'ia el gas de sus propias transacciones con la wallet que firma la operaci\'on. El backend podr\'ia implementar un mecanismo de \textit{relayer} (meta-transacciones) para que usuarios sin saldo de ETH puedan operar, pero eso a\~nade complejidad y queda fuera del alcance acad\'emico.

\textbf{-- \textquestiondown Qu\'e pasa si el usuario pierde su wallet?}

La wallet es necesaria para firmar operaciones blockchain, pero no para iniciar sesi\'on en la aplicaci\'on. El usuario puede seguir accediendo a sus documentos con su contrase\~na y 2FA. Si pierde la wallet, puede a\~nadir una nueva direcci\'on desde la configuraci\'on de cuenta. Los documentos previamente creados siguen asociados a su cuenta. Sin embargo, si no tiene copia de seguridad de la clave privada del navegador (IndexedDB), no podr\'a descifrar documentos privados compartidos por terceros hasta que se le vuelva a compartir.

\textbf{-- \textquestiondown C\'omo garantiz\'ais la privacidad si blockchain es p\'ublica?}

La blockchain solo almacena identificadores num\'ericos, hashes de contenido (CID) y direcciones Ethereum. El contenido real del documento nunca se publica en la cadena; se almacena en IPFS de forma cifrada (documentos privados) o sin cifrar (documentos p\'ublicos). Por tanto, un observador de la blockchain puede ver que existe un documento N firmado por la direcci\'on X, pero no puede acceder al contenido sin la clave sim\'etrica correspondiente.

\textbf{-- \textquestiondown Por qu\'e IPFS y no almacenamiento en nube tradicional?}

IPFS aporta direccionamiento por contenido (el CID identifica el archivo, no su ubicaci\'on), resistencia a la censura (no depende de un servidor central) y verificaci\'on de integridad autom\'atica (si el hash no coincide, el contenido ha sido alterado). Para un sistema documental que busca trazabilidad y no repudio, estas propiedades son valiosas. El almacenamiento en nube tradicional (S3, etc.) sigue siendo v\'alido para backups o para contenido p\'ublico de alto tr\'afico, pero no ofrece las mismas garant\'ias de integridad descentralizada.

\textbf{-- \textquestiondown Qu\'e ocurre si el nodo IPFS deja de funcionar?}

El sistema usa un nodo IPFS autoalojado (Kubo) dentro de Docker Compose. Si ese nodo se apaga, los documentos ya subidos dejan de estar disponibles para descarga. Sin embargo, los CIDs permanecen v\'alidos; cualquier otro nodo IPFS que tenga el contenido \textit{pinneado} puede servirlo. En un escenario de producci\'on, se recomendar\'a usar un servicio de pinning comercial (Pinata, Infura) como redundancia, o mantener m\'ultiples nodos Kubo sincronizados.

\textbf{-- \textquestiondown Por qu\'e no us\'ais una blockchain privada?}

Una blockchain p\'ublica (o de test) ofrece mayor credibilidad para la verificaci\'on externa: cualquier tercero puede consultar el contrato sin permiso. Una blockchain privada requiere controlar los nodos validadores, lo cual centraliza la confianza y reduce la ventaja diferencial respecto a una base de datos replicada tradicional. El proyecto busca demostrar que la evidencia es verificable independientemente del operador del sistema.

\textbf{-- \textquestiondown C\'omo escal\'ais con el coste del gas?}

En el alcance actual, el sistema no est\'a dise\~nado para miles de transacciones por minuto. Cada operaci\'on documental (crear, firmar, compartir) es una transacci\'on on-chain con coste de gas. Para escalar, se podr\'ia migrar a una red L2 (Polygon, Arbitrum) que reduce el coste entre 10x y 100x, o implementar \textit{rollups} que agrupan m\'ultiples operaciones en una \'unica transacci\'on L1. Estas alternativas se mencionan como trabajo futuro.

DocumentChain no es ``un Google Drive con blockchain''. La diferencia clave reside en la separaci\'on de responsabilidades entre tres capas de persistencia coordinadas:
